My Approach

Tools change; the method does not. These are the playbooks I follow, step by step, for each kind of problem. Choose a discipline to see how I work and where I have applied it.

KPIs & Business Analysis

Every analysis starts with a decision someone has to make. Before touching data, I pin down the question, the metric that answers it, and what “good” looks like.

  1. Clarify the decision and its owner

    Stakeholder interviews to capture the business question, the decision it informs, who owns it and how often it is made. The output is a one-page problem statement with scope, assumptions and success criteria that everyone signs off on.

    • Stakeholder interviews
    • Problem statement
    • Scope & assumptions
    • Success criteria

  2. Build a KPI driver tree

    Decompose the headline metric into the drivers that move it, so every number has a lever. For example, Revenue = Orders × Average Order Value and Orders = Active Customers × Purchase Frequency. When the top-line KPI moves, the tree shows which driver moved it.

    • Driver trees
    • North-star metric
    • MECE breakdown

  3. Define every KPI precisely

    Each KPI gets a written formula, grain, filters, data source, owner, refresh frequency and target, kept in a KPI dictionary so finance, operations and the dashboard all report the same number. I pair lagging indicators (revenue, churn) with leading ones (lead response time, pipeline coverage) that give an early warning.

    • KPI dictionary
    • Leading vs. lagging indicators
    • SMART targets

  4. Give every number context

    A KPI on its own means little. I report it against target, against the prior period (MoM, QoQ, YoY) and against a comparable segment, and I use rates and per-unit metrics (per customer, per order) rather than raw counts whenever volumes differ.

    • Baseline
    • Variance to target
    • Period-over-period
    • Normalised metrics

  5. Diagnose, size, recommend

    Drill down the driver tree, apply Pareto (80/20) and 5 Whys to isolate the root cause, then size the impact. Every recommendation names an owner, an action, and the KPI that will show whether it worked.

    • Root-cause analysis
    • Pareto analysis
    • Impact sizing
    • Action plan

Machine Learning

My modelling workflow is built to answer one question honestly: will this model lead to a better decision than the business makes today? That takes a clear target, leakage-free validation, and a metric chosen by the cost of being wrong.

  1. Turn the business question into an ML problem

    Define the target variable and the unit of prediction (one row = one booking, one applicant, one customer). A continuous target means regression (price, demand); a categorical outcome means classification (cancel or not, certified or denied); no label means clustering for segmentation. I check the class balance on day one because it changes every later choice.

    • Target variable
    • Regression
    • Classification
    • Clustering
    • Class balance

  2. Audit and clean the data

    Profile data types, duplicates and missing values. Impute skewed numeric columns with the median and categorical ones with the mode or an explicit “Unknown” level; correct impossible values (negative experience, zero prices) rather than silently dropping rows; and cap outliers with the IQR rule only when they are errors, not genuine extremes that carry signal.

    • Missing-value imputation
    • Duplicate removal
    • IQR outlier treatment
    • Type correction

  3. Explore with the target in mind

    Univariate distributions and skew, bivariate views of each feature against the target (for example, cancellation rate by lead-time band), and correlation heatmaps to spot multicollinearity. EDA produces hypotheses that the model then confirms or rejects.

    • EDA
    • Matplotlib / Seaborn
    • Correlation heatmap
    • Hypothesis framing

  4. Engineer features

    Create features that encode business logic: total stay length, total guests, arrival month and weekday, price per person, tenure bands. One-hot encode nominal variables (dropping one level for linear models), ordinal-encode ordered ones such as education, log-transform skewed variables such as wage or price, and scale features for distance- and gradient-based models (K-Means, logistic regression) but not for trees. For linear models I check VIF and remove features above 5.

    • Feature creation
    • One-hot & ordinal encoding
    • Log transform
    • StandardScaler
    • VIF

  5. Split without leakage

    A stratified train / validation / test split (70/30 or 60/20/20) keeps the class ratio identical in every set. Every fitted step (imputer, scaler, SMOTE) is fitted on training data only, inside a pipeline, so the test set stays genuinely unseen and the reported score is one the business can rely on.

    • Stratified split
    • Scikit-learn / imblearn Pipeline
    • Data-leakage prevention

  6. Handle class imbalance deliberately

    When the minority class is the one that matters (cancellations, denials, churners), I compare class_weight="balanced", SMOTE oversampling and random undersampling, always applied to training folds only, and then tune the decision threshold on the precision–recall curve instead of accepting the default 0.5.

    • SMOTE
    • Class weights
    • Undersampling
    • Threshold tuning

  7. Start simple, then earn complexity

    I begin with an interpretable baseline (linear or logistic regression, a shallow decision tree) and then try ensembles: Random Forest (bagging, which lowers variance) and Gradient Boosting, AdaBoost or XGBoost (boosting, which lowers bias). A complex model has to beat the baseline by enough to justify the explainability it gives up.

    • Logistic Regression
    • Decision Tree
    • Random Forest
    • Gradient Boosting
    • XGBoost

  8. Tune and validate

    Stratified 5-fold cross-validation with GridSearchCV or RandomizedSearchCV over depth, minimum samples per leaf, number of estimators and learning rate; cost-complexity pruning (ccp_alpha) for decision trees. I compare train and test scores side by side to catch overfitting before it reaches a stakeholder.

    • Stratified K-Fold
    • GridSearchCV
    • Cost-complexity pruning
    • Overfitting checks

  9. Explain it and recommend

    Feature importance (impurity-based and permutation), logistic-regression coefficients read as odds ratios, and a confusion matrix translated into business terms: how many at-risk cases the model catches, and how many good customers it wrongly flags. The deliverable is a recommendation, not a score.

    • Feature importance
    • Odds ratios
    • Confusion matrix
    • Business recommendation

Choosing the Model

Problem Where I start When I move up
Regression Linear Regression, checking linearity, normality of residuals, homoscedasticity and VIF Ridge / Lasso for multicollinearity or feature selection; Random Forest or Gradient Boosting Regressor for non-linear effects and interactions
Classification Logistic Regression for interpretable odds ratios; a pruned Decision Tree for rules stakeholders can follow Random Forest when a single tree overfits (high variance); Gradient Boosting / XGBoost when bias remains and predictive power matters most
Segmentation K-Means on scaled features, with k chosen by the elbow method and silhouette score Hierarchical clustering (Ward linkage, dendrogram, cophenetic correlation) to validate the structure; every cluster is profiled before it is named

Choosing the Metric

Metric I use it when Typical case
Accuracy Classes are balanced and both errors cost the same Rarely my headline metric
Precision False positives are expensive Sending manual reviews or retention offers to cases that did not need them
Recall False negatives are expensive Missing a booking about to cancel, a customer about to churn, or a fraudulent transaction
F1 score Both errors matter and the classes are imbalanced Hotel cancellations: an empty room and an overbooked guest both cost money
ROC-AUC / PR-AUC Comparing models independently of the threshold; PR-AUC under heavy imbalance Shortlisting models before threshold tuning
RMSE / MAE / MAPE Regression: RMSE penalises large misses, MAE reads in business units, MAPE gives a percentage error Forecasting price or demand
R² / Adjusted R² Explaining variance in linear models; adjusted R² penalises features that add nothing Linear regression diagnostics
Silhouette / Elbow Choosing the number of clusters and checking how well they separate Customer segmentation

SQL

I write SQL that someone else can read, rerun and trust: understand the grain first, validate before aggregating, and build complex logic in small, testable steps.

  1. Learn the schema and the grain

    Map the tables, primary and foreign keys, and what one row represents (an order, an order line, a customer). Knowing the grain is what prevents a join from fanning out and silently double-counting revenue.

    • ER diagram
    • Primary / foreign keys
    • Grain
    • Join cardinality

  2. Validate before analysing

    Row counts, COUNT(*) against COUNT(DISTINCT key) to catch duplicates, NULL profiling, minimum and maximum dates, and orphan checks with LEFT JOIN … WHERE key IS NULL. Totals are reconciled against the source before any insight is shared.

    • Data profiling
    • Duplicate checks
    • NULL handling
    • Reconciliation

  3. Build in readable steps with CTEs

    Each CTE does one job (filter, join, aggregate, rank) and can be tested on its own. I filter early, select only the columns I need, and name outputs in business language rather than database shorthand.

    • CTEs
    • Subqueries
    • CASE WHEN
    • Clear naming

  4. Turn tables into KPIs

    GROUP BY / HAVING and conditional aggregation (SUM(CASE WHEN …)) for revenue, order volume, average order value, repeat-customer rate, ratings and delivery time (DATEDIFF between order and ship dates).

    • Aggregations
    • Conditional aggregation
    • Date functions
    • KPI queries

  5. Use window functions for trends and ranking

    LAG / LEAD for quarter-over-quarter change, SUM() OVER (ORDER BY …) for running totals, RANK / DENSE_RANK for top-N per group, ROW_NUMBER to de-duplicate to the latest record, and NTILE for RFM-style segmentation.

    • LAG / LEAD
    • Running totals
    • RANK / DENSE_RANK
    • ROW_NUMBER
    • NTILE

  6. Drill down to the root cause

    When a KPI moves, I decompose it through its driver tree and slice by time, region, product and customer segment until the change is isolated to one driver that the business can act on.

    • Root-cause analysis
    • Segmentation
    • Cohort analysis

  7. Keep it fast and correct

    Index join and filter keys, keep predicates sargable (no functions wrapped around indexed columns), read the EXPLAIN plan on slow queries, and document assumptions alongside the query so the result can be audited.

    • EXPLAIN plans
    • Indexing
    • Query optimisation
    • Documentation

Example: quarter-over-quarter revenue with a CTE and a window function

WITH quarterly AS (
    SELECT quarter_number,
           SUM(quantity * vehicle_price) AS revenue,
           COUNT(DISTINCT order_id)      AS orders
    FROM   orders
    GROUP  BY quarter_number
)
SELECT quarter_number,
       revenue,
       orders,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY quarter_number))
             / LAG(revenue) OVER (ORDER BY quarter_number), 1) AS revenue_qoq_pct
FROM   quarterly
ORDER  BY quarter_number;

Where I Have Applied This

Revenue & operations analysis: queried 1,000 orders from 984 customers across 49 U.S. states to track quarterly revenue, orders and ratings. Traced a 39% revenue decline to a 60% rise in shipping time (28 to 45 days) and proposed a 25-day shipping SLA.

Power BI / Tableau

A dashboard has done its job if the person reading it knows what to do next within ten seconds. I design backwards from that decision.

  1. Start from the audience and its decisions

    Executives need four to six headline KPIs with trend and variance to target; analysts need drill-down. Before building, I agree KPI definitions, refresh frequency and access rules with the people who will use the report.

    • Requirements
    • KPI dictionary
    • Audience mapping

  2. Model the data as a star schema

    Fact tables at a clear grain, surrounded by dimension tables (Date, Customer, Product, Region) with one-to-many, single-direction relationships and a dedicated Date table for time intelligence. Cleaning and shaping happen upstream in Power Query: data types, unpivoting, merges and appends, de-duplication.

    • Star schema
    • Fact & dimension tables
    • Date table
    • Power Query (M)

  3. Write measures, not hard-coded numbers

    Power BI: DAX measures built on CALCULATE and filter context, DIVIDE for safe ratios, time intelligence (TOTALYTD, SAMEPERIODLASTYEAR, DATEADD) and variables for readability. Tableau: calculated fields, LOD expressions (FIXED, INCLUDE, EXCLUDE) for customer-level metrics, table calculations for running totals and percent of total, and parameters for what-if analysis and metric switching.

    • DAX
    • CALCULATE
    • Time intelligence
    • LOD expressions
    • Parameters

  4. Lay it out for a ten-second read

    KPI cards with variance to target and to the prior period across the top, the trend in the middle, breakdowns and detail below, following the natural Z-pattern. Line charts for trends, sorted bars for comparisons, no 3-D and no pie with more than a few slices, and one accent colour reserved for what needs attention.

    • KPI cards
    • Visual hierarchy
    • Chart selection
    • Conditional formatting

  5. Add interaction with intent

    Slicers and filters for the questions users actually ask, drill-through and tooltip pages for detail on demand, bookmarks and Tableau story points to walk through a narrative, and dashboard actions to filter across sheets.

    • Drill-through
    • Report tooltips
    • Bookmarks
    • Dashboard actions
    • Story points

  6. Make it fast, secure and trusted

    Remove unused and high-cardinality columns, prefer Import mode with incremental refresh where the data allows, apply row-level security so each manager sees only their region, and reconcile every KPI against the source system before release.

    • Performance tuning
    • Incremental refresh
    • Row-level security
    • Validation

  7. Close with the “so what”

    Every page carries an annotated insight and a recommendation, so the dashboard drives action instead of just reporting numbers.

    • Insight annotation
    • Recommendations
    • Adoption

Where I Have Applied This

Car insurance claims (Tableau): built a six-part interactive story with calculated fields, parameters and an executive KPI dashboard. The analysis showed that SUVs and blue-collar drivers account for the highest claims, which led to a recommendation for risk-based premium pricing.

Excel

Excel is where many stakeholders live, so I build workbooks they can open, audit and refresh themselves.

  1. Clean with Power Query, not by hand

    Repeatable import, type setting, trimming, splitting and de-duplication, so next month’s file refreshes in one click instead of being rebuilt.

    • Power Query
    • Data types
    • Refreshable workflow

  2. Structure the workbook

    Separate input, calculation and output sheets; store data as Excel Tables with structured references; keep assumptions in one clearly marked place and never hard-code numbers inside formulas.

    • Excel Tables
    • Structured references
    • Input / calc / output

  3. Analyse with the right functions

    XLOOKUP and INDEX-MATCH for lookups, SUMIFS / COUNTIFS / AVERAGEIFS for conditional metrics, PivotTables for fast slicing, and Goal Seek or data tables for what-if scenarios.

    • XLOOKUP
    • SUMIFS / COUNTIFS
    • PivotTables
    • What-if analysis

  4. Present it as a dashboard

    PivotCharts driven by slicers and timelines, conditional formatting to flag exceptions, and a one-page summary sheet that leads with the answer.

    • PivotCharts
    • Slicers & timelines
    • Conditional formatting
