AutoSQL Explorer

Upload a set of tables and it learns the schema, checks the data before trusting it, writes the analysis as readable MySQL or PostgreSQL, runs it, and explains every number in plain English. It ends with a one-page business brief a manager can act on.

Approach

I write SQL that someone else can read, rerun and trust, so I turned that habit into a pipeline where every decision is a written rule rather than a black box.

  • Schema first. Each table’s key and grain (what one row is), every foreign key, and how many rows join to one, so a join can’t silently multiply a total.
  • Validate before analyzing. Duplicates, NULLs, impossible values, orphans and partial periods are checked, and revenue is reconciled to the cent between the raw table, the views and an independent pandas recomputation.
  • One statement, three dialects. Each query is written once as small CTE steps and rendered for MySQL 8 and PostgreSQL (shown) and DuckDB (run inside the app), so no database server is needed.
  • Explanations written from the result. Every step says what was found, why it matters and what it does next. The closing finding is generated by code from the actual output, so the text can’t contradict the numbers, and every change carries a 95% confidence interval.
  • From numbers to a decision. A data-trust score, prioritized recommendations with their evidence and SQL, and a self-contained HTML brief that works offline.

Issues & Fixes

Issue How I dealt with it
SQL that ran fine in DuckDB broke on real databases: ROUND(double, 1) doesn’t exist in PostgreSQL, count / count truncates to 0 there, and lines is a reserved word in MySQL. Tested the exported project on live PostgreSQL and MySQL, and turned each difference into a rule the tests enforce: every division is guarded with NULLIF, PostgreSQL rounds on numeric, and reserved words are never used as aliases.
The data ended on 6 May, so the “latest quarter” looked like a 52.4% collapse. Partial periods are shown but never compared. The real change between the last two complete quarters was +64.3%, and periods of different lengths are compared per day.
Noise reported as a result: order value up 8.3% was colored green, though its 95% interval ran from −20% to +37%. A confidence interval on every change, with a “within normal variation” label. A simulation on pure-noise data showed the unusual-period rule also fired too often, so it now needs a 99% prediction interval on both level and trend.
NTILE(5) split tied customers by their ID, so 34 of 89 customers got a frequency score decided by their ID rather than their orders. Switched to CEIL(5 × CUME_DIST()), so customers with equal values always get equal scores.
A one-million-row upload took about 15 seconds, because profiling ran a regular expression on every value. Loading and profiling now work on distinct values and map the answers back, and a golden snapshot test proves the results stayed identical. About 6 seconds now.

Limitations

  • One fact table and one revenue formula: no cost or margin, no currency conversion, and no second fact table (returns or targets) in the same analysis.
  • Business rules are recognized by column names and values, so a rule hidden in a code (type = 7) is missed.
  • Calendar periods only: no fiscal years or 4-4-5 retail weeks.
  • The confidence intervals assume orders arrive independently, and each KPI tile is tested on its own, with no correction for testing several at once.
  • A driver that moved with revenue is reported as a candidate cause that “needs a test”, never as proof.
  • Uploads are read into memory, so size is limited by the machine, and there is no hosted version yet: it runs locally with Streamlit.

Approach

Spreadsheets slow down around a million rows and notebooks need setup, so I built an analysis engine that streams the file and never holds it in memory.

  • One pass, mergeable summaries. Each worker keeps sums, counts, hash tables and sketches for its slice of the file. The slices simply add together, so the work splits across CPU cores without any coordination.
  • Streams in 4 MB chunks. Memory stays flat whether the file is 1 MB or 13.8 GB.
  • Honest accuracy. Counts, means, standard deviations, correlations and group means are exact. Medians and percentiles are exact up to about 2 million rows (and for whole numbers at any size); beyond that they come from a sketch accurate to 0.1% and are marked “≈”.
  • No server. React views, a dependency-free JavaScript engine in Web Workers, IndexedDB storage, and GitHub Actions that test, build and deploy to GitHub Pages.
  • From statistics to answers. Plain-language insights, a decision summary, chart downloads (PNG, SVG, CSV) and a starter Jupyter notebook that keeps the real column names.

Issues & Fixes

Issue How I dealt with it
The silent sample: statistics described only the first 110,000 rows, so a file sorted by date reported only its oldest data, and nothing warned about it. Built the streaming engine so every row is read, and the app now says which numbers are exact and which are estimates.
Saved datasets disappeared on reload, because localStorage holds only about 5 MB. Moved storage to IndexedDB with an automatic migration. Files up to 512 MB now survive a reload.
The same engine ran 15× slower in the browser than in Node. Profiled it, split one huge per-row function into small ones the JIT compiler can optimize, and replaced Map with typed-array hash tables: one worker went from 5 to 24 MB/s.
A text column with 60,000 unique values froze the app: after pruning, the hash table size wasn’t a power of two, so probing never found a free slot. A one-line rounding fix, a cap on tracking new values after three prunes, and a regression test that finishes in under a second.
The row estimate was about 5× too high, which pushed a 1M-row file out of exact mode. Estimated bytes per row from every row in the first 1 MB instead of a 5,000-row sample: 1.04M estimated for a real 1.0M.

Approach

Most AutoML tools hand you a score with no reasoning. I wanted one that shows its judgement, so it generates readable code instead of hiding a library call.

  • Profile roles, not just types. Every column is classed as a number, category, date, ID, constant or free text, with a reason, so an ID is dropped instead of memorized.
  • A transparent rule engine. Quality gates, then task, model and sampling. Every choice is recorded with what was found, why it matters and what happens next.
  • Generate the code, then run it. What you see is exactly what ran, each finding is written by the code from the real results, and the whole analysis downloads as a Jupyter notebook.
  • Honest evaluation. Imputation, scaling, resampling, tuning and the decision threshold all happen inside the training folds of a pipeline. The test set is touched once, against a baseline.
  • Compare, don’t assume. The rule-of-thumb model becomes one candidate among linear, tree, forest and boosting models, and cross-validation picks the winner.

Issues & Fixes

Issue How I dealt with it
Column names were pasted into the generated code, so a quote or {x} in a name broke it: a code-injection risk. Names now reach the generated code only through repr() or runtime variables, with a test that tries hostile names.
Hidden duplicates: Booking_ID made every row unique, so my hand-made notebook reported 0 duplicates while 28% of rows had a twin. Duplicates are checked with IDs ignored, and the model is also scored on test rows with no twin in training: 0.841 against 0.884, the number I would quote.
The original app said SMOTE was applied when it never was. Resampling became a real, measured step inside the cross-validation folds, compared against class weights.
Tuning sometimes adopted settings that scored worse than the defaults. Tuned settings are kept only if they beat the default cross-validated score.
On macOS, LightGBM was “installed” but couldn’t load (missing libomp), which crashed the run. The engine really imports each optional library once. If that fails, the model is skipped and the decision trace says what to install.

Limitations

  • The train/test split is random, not time-aware, which flatters a model meant to predict future bookings.
  • Large files are sampled (50,000 rows for forests, 10,000 for comparison and tuning), and it hasn’t been tested beyond 200,000 rows or about 20 columns.
  • Probabilities aren’t calibrated, and there are no per-row (SHAP) explanations.
  • The cost-based decision threshold exists as code in the roadmap, not in the app.

Approach

A wrong p-value looks exactly like a right one, so I built two engines that have to agree.

  • Hybrid statistics. Every analysis runs on the device first (instant, and it validates the input), then asks a FastAPI service built on SciPy and statsmodels for the authoritative result when it is reachable. A badge says which engine produced each number.
  • Double-precision maths in TypeScript. Cody’s normal CDF, the AS 241 quantile and an incomplete-beta Student’s t distribution, tested against SciPy reference values.
  • Guardrails before verdicts. A sample ratio mismatch blocks the call, reading results before the planned sample size triggers a peeking warning, and a significant loss recommends a rollback.
  • Local first. Experiments are saved in the browser. Magic-link sign-in and a cloud archive (Supabase with row-level security) are optional.
  • Stories that can’t drift. Nine personas follow an experiment from plan to decision, and every figure in their text is computed when the page renders and pinned by a test.

Issues & Fixes

Issue How I dealt with it
The prototype’s z-test used the wrong standard error for its test statistic, and only knew the critical values for 90%, 95% and 99% confidence. The pooled standard error for the test and the unpooled one for the interval, as the method requires, with exact critical values for any confidence level.
Its normal-distribution approximation was accurate to only about 10−7. Replaced it with double-precision algorithms, checked against SciPy to about 10−12.
The prototype stored passwords in plain text in the browser. The new version re-analyzes saved experiments with the corrected engine, imports them, and deletes the password store. Sign-in moved to an optional magic link.
The statistics service template returned server errors on NumPy booleans, lost precision on very small p-values, accepted any origin with credentials, and flipped the sign of the CUPED t statistic. Fixed each one, using survival functions for tail probabilities and an explicit list of allowed origins, then added input validation and a pytest suite.
Numbers were formatted differently by Node and by browsers, which broke page hydration. Wrote a compact number and money formatter that doesn’t depend on the platform.

Approach

It started as my Colab notebook on clinical decision support with the Merck Manual, where retrieval lifted groundedness from 3.6 to 5.0 out of 5. I rebuilt it as a free website that works on any document.

  • Ingestion off the main thread. Files are parsed (PDF, Word, HTML, Markdown, text), cleaned of watermarks and running headers, split into section-aware chunks of 400 tokens with a 50-token overlap, and indexed with BM25 in a Web Worker.
  • Hybrid retrieval. BM25 and embedding similarity merged with Reciprocal Rank Fusion, with optional reranking, neighbor expansion, HyDE and a corrective retry when grounding is weak.
  • Evaluation on every answer. LLM-as-a-judge groundedness and relevance, a sentence-level claim-support map, citation accuracy, a confidence rating and a timing breakdown. An Evaluation Lab reports hit@k, recall@k and MRR.
  • Bring your own model. Free options (extractive, in-browser, Hugging Face, a local Ollama) or your own key for Claude, DeepSeek, OpenAI, Gemini, Groq, Mistral or OpenRouter.
  • Privacy by design. Documents and indexes stay in the browser’s IndexedDB, a cloud model sees only the excerpts behind each answer, API keys stay in memory, and Confidential mode blocks anything that would leave the device.

Issues & Fixes

Issue How I dealt with it
The whole chat session was written to IndexedDB on every streamed token. It is saved only when an answer changes phase: about 5 writes per answer.
Float32 vectors took about 21 MB for 14,000 chunks and were rewritten every 15 seconds. int8 vectors with a per-row scale, saved in 1,024-row shards: 4× smaller, searched with a bounded min-heap.
Big books froze the page while they were cleaned, chunked and indexed. Moved ingestion into a Web Worker, with compact typed-array postings for BM25.
Starter questions quietly spent Hugging Face credits, and the token check ran a billed generation. Starter questions now come from section titles (AI-written ones are opt-in), the token check uses a free endpoint, and a usage meter shows calls and tokens.
A background refresh could rewind an answer that was still streaming. Sessions reload only when the active collection changes.

Limitations

  • The embedding model (23–34 MB) downloads on first use, and embedding a 4,000-page book without a GPU is slow, although keyword search works in the meantime.
  • Groundedness is measured against the retrieved passages, not against the truth, so a retrieval miss can still score well.
  • Scanned, image-only PDFs can’t be indexed yet, because there is no OCR.
  • A collection is limited by one browser’s storage, and stored documents aren’t encrypted by the app.
  • Some providers block calls made straight from a web page; OpenRouter is the workaround.
  • Answers support research and decisions; they don’t replace professional judgement.

Future Improvements

  • An optional server mode with a vector database, for collections too big for one browser.
  • Stronger evaluation: NLI-based faithfulness, a judge that differs from the answering model, and generated question sets.
  • Shareable collections and multilingual embeddings.

Approach

A portfolio should load fast, read well on any device and be honest about what is finished, so I kept it static and put the effort into content and accessibility.

  • Static on GitHub Pages. Plain HTML pages on HTML5 UP’s Forty template, with my own stylesheet layered on top so the template’s files change as little as possible, and a small script for the tabs.
  • Content from my resume and real work. An experience timeline, skills and certifications, and an approach that runs through six stages, from the question and KPIs to the decision, with worked examples in SQL, Python, DAX and Excel.
  • One layout for every track. Each project page shares the same structure: what the track covers, the skills it uses, and its case studies.
  • Accessible by default. A keyboard-friendly menu and tabs, visible focus, readable contrast over images, reduced motion, and pages that still work without JavaScript or on paper.

Issue How I dealt with it
